# Prayer Schedule agent guide

## Project

Prayer Schedule is a Nuxt 4 / Vue 3 application deployed as a Cloudflare Worker. It stores prayers, content blocks, schedules, and per-user progress in Cloudflare D1.

## Where things live

- `app/pages`: route-level UI and orchestration.
- `app/components`: reusable UI.
- `app/composables`: reusable client state and behavior.
- `shared`: types and domain logic shared by client and server.
- `server/api`: thin HTTP handlers.
- `server/domain`: server-side application/domain behavior.
- `server/repositories`: D1 persistence.
- `db/migrations`: authoritative database evolution.
- `db/dev`: local reset and seed helpers; do not evolve the schema here.

## Generated files

`worker-configuration.d.ts` is generated by `npm run cf-typegen` and is intentionally tracked for Cloudflare binding types. Agents must ignore it during repository discovery, search, review, and context gathering unless the task concerns Cloudflare bindings or generated environment types. Do not hand-edit it.

Likewise, ignore `.nuxt`, `.output`, `.wrangler`, `dist`, and `node_modules` unless the task specifically requires generated output.

## Development

```bash
npm install
npm run dev
```

The development server uses the `dev` bindings in `wrangler.jsonc`. Local D1 data can be rebuilt with `npm run db:fresh`.

## Validation

For a normal code change, run:

```bash
npm run check
```

Add focused tests for extracted domain behavior and regressions. Run `npm run test`, `npm run typecheck`, and `npm run build` separately when diagnosing which gate failed.

Before deployment, run `npm run check:deploy`. Browser tests start an isolated local server with an explicitly guarded test-session bypass; the bypass is unavailable in production.

## Conventions

- Keep pages and API routes focused on orchestration.
- Put shared prayer shapes and pure transformations in `shared/prayer`.
- Put server application logic in `server/domain` and D1 statements in `server/repositories`.
- Use migrations for every database change.
- Preserve Catholic terminology and devotional meaning; do not replace it with generic wellness language.
- Avoid `any` for prayer data. Prefer the shared discriminated content-block types.
